**Варианты ответов:**

| Для анализа выполнения требований | Трассировка не является частью требований | Для создания новых требований | Для отслеживания связи между требованиями на разных уровнях |
| --------------------------------------------------------------- | ------------------------------------------------------------------------------ | ------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------- |

**✅ Правильный ответ:** **Для отслеживания связи между требованиями на разных уровнях**

- Функциональными требованиями
- Техническими спецификациями
- Тест-кейсами

7. **Трассируемость** — связи с другими требованиями, тестами, задачами
8. **Критерии приёмки** — условия, при которых требование считается выполненным

📌 **Объяснение:** Эти атрибуты позволяют полноценно управлять требованиями: отслеживать их состояние, контролировать изменения, обеспечивать трассируемость от бизнес-целей до реализации и тестирования.

(Варианты не указаны — вопрос требует понимания практики трассировки требований)

### 17. 📋 **Вопрос: Что описывает диаграмма классов UML?**

**Варианты ответов:**
(Варианты не указаны — вопрос требует знания UML)

**✅ Что описывает диаграмма классов UML:**

Диаграмма классов UML описывает **статические структуры системы**:

1. **Классы** — их атрибуты и методы
2. **Отношения между классами**:
   - Ассоциации
   - Наследование
   - Агрегация/композиция
   - Зависимости
3. **Интерфейсы**
4. **Перечисления (enum)**

**Пример:**

- Класс `Заказ` с атрибутами `номер`, `дата`, `сумма`
- Класс `Клиент` с атрибутами `имя`, `адрес`
- Связь: `Клиент` → `Заказ` (ассоциация "один-ко-многим")

📌 **Объяснение:** Диаграмма классов показывает структуру системы на уровне объектов, их свойств и взаимосвязей, но **не** показывает поведение или последовательность действий (это делают диаграммы последовательности, активностей и др.).

### 18. 📋 **Вопрос: В чём разница между Use Case (UC) и User Story (US)?**

**✅ Сравнение Use Case и User Story:**

| Критерий                 | Use Case (UC)                                                                                                            | User Story (US)                                                                                                                      |
| -------------------------------- | ------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------ |
| **Формат**           | Детализированный сценарий с основным и альтернативными потоками | Короткое описание в формате "Как [роль], я хочу [функция], чтобы [ценность]" |
| **Детализация** | Высокая (предусловия, постусловия, шаги)                                                | Низкая (описание намерения)                                                                                   |
| **Уровень**         | Системный уровень (система как чёрный ящик)                                          | Пользовательский уровень (потребности пользователя)                                    |
| **Объём**             | Один UC может охватывать несколько US                                                        | Одна US обычно соответствует части UC                                                                    |
| **Цель**               | Описать все возможные сценарии взаимодействия                                   | Сформулировать потребность для планирования спринта                                   |

📌 **Объяснение:**

- **Use Case** — это полноценная спецификация взаимодействия пользователя с системой, документ для аналитиков и разработчиков
- **User Story** — это инструмент Agile для планирования, фокус на ценности для пользователя, а не на технической реализации

### 19. 📋 **Вопрос: Разрабатывая систему для управления складом, важно мгновенно уведомить менеджера о поступлении нового товара. Какой механизм лучше всего подходит для этой задачи?**

**Варианты ответов:**

| Настройка webhook для отправки уведомлений в реальном времени | [Вариант 2] | [Вариант 3] |
| ------------------------------------------------------------------------------------------------------------ | ------------------ | ------------------ |
| ✅                                                                                                           | ❌                 | ❌                 |

**✅ Правильный ответ:** **Настройка webhook для отправки уведомлений в реальном времени**

📌 **Объяснение:**

- **Webhook** — это механизм мгновенных (real-time) уведомлений, когда система отправляет HTTP-запрос на указанный URL при наступлении события (поступление товара)
- **Альтернативы** (возможные другие варианты в вопросе):
  - Периодический опрос (polling) — не мгновенный, создаёт задержки
  - Email-рассылка — может быть не мгновенной
  - Сохранение в лог-файл — требует ручной проверки
- **Webhook** идеален для мгновенных уведомлений в реальном времени через мессенджеры, push-уведомления или внутренние системы

| -------------- | ----------------------------------------------------- | ---------- |
| ❌             | ❌                                                    | ✅         |

**Вариант с кэшированием** частично верен, но не является основной причиной stateless архитектуры.

### 38. 📋 **Вопрос: Твоя команда разрабатывает CRM. Есть дублирование "Клиент" и "Контрагент". Какова основная ошибка в этом случае?**

**Варианты ответов:**

1. Игнор потребностей пользователей
2. Отсутствие четкой формулировки бизнес-целей
3. Неправильное определение границ сущностей
4. Неправильное именование сущностей

**Правильный ответ:** 3. Неправильное определение границ сущностей.

Дублирование сущностей возникает из-за нарушения bounded context: "Клиент" и "Контрагент" описывают один бизнес-объект с разными аспектами (физлицо vs юрлицо), но без четких границ приводят к нормализационным проблемам и дубликатам данных. Нужно объединить в единую сущность с подтипами (inheritance или single table).
