Вопрос 1

Какой этап жизненного цикла разработки IT-системы предшествует фазе проектирования?

📌 Объяснение:
Фазе проектирования всегда предшествует этап сбора и анализа требований (информации), чтобы понять, что именно нужно разрабатывать.
Вопрос 2

На каком этапе жизненного цикла разработки происходит создание программного продукта на основе утвержденных требований?

📌 Объяснение:
Создание программного продукта (написание кода) происходит на этапе разработки, который следует после сбора требований и проектирования, но до тестирования и внедрения.
Вопрос 3

Какой этап включает в себя развертывание разработанной системы в реальной среде и обеспечивает ее стабильной работы?

📌 Объяснение:
Этап внедрения (deployment) включает развертывание системы в реальной рабочей среде, настройку, обучение пользователей и обеспечение начальной стабильной работы. Сопровождение начинается после успешного внедрения.
Вопрос 4

Что представляет собой декомпозиция в контексте управления проектом?

📌 Объяснение:
Декомпозиция — это метод управления проектами, при котором сложная задача разбивается на более мелкие, понятные и управляемые части (подзадачи), что упрощает планирование, оценку и контроль выполнения проекта.
Вопрос 5 (несколько вариантов)

Какие характеристики стейкхолдеров помогут оценить их значительность для проекта?

📌 Объяснение:
Для оценки значимости стейкхолдеров в проекте анализируют все три характеристики:

1. Доступ к ресурсам и экспертизе — может ли стейкхолдер предоставить необходимые ресурсы или знания
2. Полномочия и ответственность за принятие решения — уровень влияния на ключевые решения
3. Их роль и влияние на проект — как они могут повлиять на успех или неудачу проекта

Все эти факторы вместе помогают определить приоритеты работы со стейкхолдерами.
Вопрос 6

Какая информация является наиболее полной и полезной для включения в каталог стейкхолдеров?

📌 Объяснение:
Наиболее полная информация о стейкхолдере должна включать не только идентификационные данные (имя, контакты), но и характеристики, важные для управления их вовлеченностью:

- Роль в системе — какую функцию выполняет
- Уровень полномочий — степень влияния на проект
- Интересы и зоны ответственности — что важно для стейкхолдера и за что он отвечает

Это позволяет эффективно выстраивать коммуникацию и управлять ожиданиями.
Вопрос 7

Какие категории заинтересованных сторон могут быть сгруппированы по ролям в рамках проекта?

📌 Объяснение:
Группировка стейкхолдеров по ролям обычно основывается на:

- Выполняемых задачах (функциональная роль в проекте)
- Схожих интересах к результатам проекта
- Принадлежности к внутренним/внешним группам

Это позволяет эффективно управлять коммуникацией и учитывать потребности схожих категорий участников, а не рассматривать каждого стейкхолдера индивидуально.
Вопрос 8

Что представляют собой бизнес-требования?

📌 Объяснение:
Бизнес-требования — это высокоуровневые цели, которые организация или заказчики хотят достичь с помощью системы. Они отвечают на вопрос "Зачем нужна система?" и описывают ожидаемую бизнес-ценность, а не технические детали или внутренние характеристики.
Вопрос 9

Какие требования описывают ожидаемое поведение системы при определенных условиях?

📌 Объяснение:
Функциональные требования определяют, что система должна делать — её поведение, функции и реакции на различные входные данные и условия. Они описывают конкретные действия системы: "Если пользователь нажимает кнопку X, то система выполняет Y".
Вопрос 10

Что из перечисленного является основными этапами управления требованиями?

📌 Объяснение:
Основные этапы управления требованиями согласно стандартам (например, BABOK):

1. Идентификация — выявление требований от стейкхолдеров
2. Анализ — уточнение и детализация требований
3. Спецификация — документирование требований
4. Контроль — управление изменениями и трассируемостью требований
Вопрос 11

Зачем проводится трассировка требований?

📌 Объяснение:
Трассировка требований (requirements traceability) — это процесс отслеживания связей между:

- Бизнес-требованиями
- Функциональными требованиями
- Техническими спецификациями
- Тест-кейсами

Это позволяет убедиться, что все высокоуровневые цели реализованы в системе, а также быстро оценить влияние изменений в требованиях на другие элементы проекта.
Вопрос 12

Какие атрибуты необходимо учитывать при управлении требованиями для обеспечения их полноты и отслеживаемости?

📌 Объяснение:
Типичные атрибуты требований для полноты и отслеживаемости:

1. ID — уникальный идентификатор требования
2. Приоритет — важность требования (высокий/средний/низкий)
3. Источник — кто выдвинул требование (стейкхолдер)
4. Статус — текущее состояние (новое/утверждённое/реализованное и т.д.)
5. Версия — номер версии требования
6. Сложность — оценка трудности реализации
7. Трассируемость — связи с другими требованиями, тестами, задачами
8. Критерии приёмки — условия, при которых требование считается выполненным

Эти атрибуты позволяют полноценно управлять требованиями: отслеживать их состояние, контролировать изменения, обеспечивать трассируемость от бизнес-целей до реализации и тестирования.
Вопрос 13

Вам поручено подготовить проектную документацию/управление требованиями. Какой инструмент для управления требованиями лучше выбрать?

📌 Объяснение:
- Jira — специализированный инструмент для управления проектами и требованиями, поддерживает трассировку, приоритизацию, статусы, связи между задачами
- Trello — больше подходит для визуального управления задачами, но не для комплексного управления требованиями
- Excel/Google Sheets — табличные редакторы, не предоставляют встроенных возможностей для управления жизненным циклом требований, трассируемости и интеграции с разработкой

Jira позволяет эффективно управлять требованиями на протяжении всего жизненного цикла проекта.
Вопрос 14

Процесс управления изменениями требований включает в себя несколько ключевых этапов?

📌 Объяснение:
Процесс управления изменениями требований (Change Control Process) обычно включает:

1. Идентификация изменения — запрос на изменение
2. Анализ влияния — оценка последствий для сроков, бюджета, архитектуры
3. Согласование — утверждение изменения с ключевыми стейкхолдерами
4. Реализация — внесение изменения и обновление документации
5. Верификация — проверка, что изменение корректно реализовано
Вопрос 15

Каким образом требования могут быть привязаны к задачам в системе управления проектами?

📌 Объяснение:
Основные способы привязки требований к задачам:

1. Ссылочная трассировка — требование и задача связаны по ID
2. Иерархическая структура — задача создаётся как подэлемент требования
3. Специальные поля/теги — в задаче указывается ID связанного требования
4. Интеграция через инструменты — Jira ↔ Confluence, Trello с карточками требований
5. Матрица трассируемости — таблица связей между требованиями и задачами

Привязка требований к задачам обеспечивает трассируемость — возможность отслеживать, какое требование реализуется в какой задаче, и контролировать полноту реализации всех требований в проекте.
Вопрос 16

Ты проводишь интервью с клиентом для сбора требований к новой системе учёта запасов. Какую из следующих сущностей вам следует обсудить в первую очередь?

📌 Объяснение:
При сборе требований к системе учёта запасов нужно начинать с базовых сущностей (core entities), которые являются центральными для предметной области:

1. Товары — что хранится (основной объект учёта)
2. Складские помещения — где хранится
3. Поставки — как поступает
4. Заказы — как расходуется

Начинать с товаров логично, так как без понимания того, что учитывается, нельзя проектировать учёт где, как и когда.
Вопрос 17

Что описывает диаграмма классов UML?

📌 Объяснение:
Диаграмма классов UML описывает статические структуры системы:

1. Классы — их атрибуты и методы
2. Отношения между классами:
   - Ассоциации
   - Наследование
   - Агрегация/композиция
   - Зависимости
3. Интерфейсы
4. Перечисления (enum)

Пример:
- Класс Заказ с атрибутами номер, дата, сумма
- Класс Клиент с атрибутами имя, адрес
- Связь: Клиент → Заказ (ассоциация "один-ко-многим")

Диаграмма классов показывает структуру системы на уровне объектов, их свойств и взаимосвязей, но не показывает поведение или последовательность действий (это делают диаграммы последовательности, активностей и др.).
Вопрос 18

В чём разница между Use Case (UC) и User Story (US)?

📌 Объяснение:
Сравнение Use Case и User Story:

КритерийUse Case (UC)User Story (US)
ФорматДетализированный сценарий с основным и альтернативными потокамиКороткое описание в формате "Как [роль], я хочу [функция], чтобы [ценность]"
ДетализацияВысокая (предусловия, постусловия, шаги)Низкая (описание намерения)
УровеньСистемный уровень (система как чёрный ящик)Пользовательский уровень (потребности пользователя)
ОбъёмОдин UC может охватывать несколько USОдна US обычно соответствует части UC
ЦельОписать все возможные сценарии взаимодействияСформулировать потребность для планирования спринта
- Use Case — это полноценная спецификация взаимодействия пользователя с системой, документ для аналитиков и разработчиков
- User Story — это инструмент Agile для планирования, фокус на ценности для пользователя, а не на технической реализации
Вопрос 19

Разрабатывая систему для управления складом, важно мгновенно уведомить менеджера о поступлении нового товара. Какой механизм лучше всего подходит для этой задачи?

📌 Объяснение:
- Webhook — это механизм мгновенных (real-time) уведомлений, когда система отправляет HTTP-запрос на указанный URL при наступлении события (поступление товара)

Альтернативы:
- Периодический опрос (polling) — не мгновенный, создаёт задержки
- Email-рассылка — может быть не мгновенной
- Сохранение в лог-файл — требует ручной проверки

Webhook идеален для мгновенных уведомлений в реальном времени через мессенджеры, push-уведомления или внутренние системы.
Вопрос 20

Ваша команда разрабатывает API для онлайн-кинотеатра. Как обеспечить безопасность и управление доступом к ресурсам?

📌 Объяснение:
Для безопасности API онлайн-кинотеатра необходимо:

1. Идентификация и аутентификация — проверка, кто обращается к API (например, через OAuth, JWT-токены, API-ключи)
2. Авторизация — проверка прав доступа к конкретным ресурсам (фильмам, функциям)

Остальные варианты недостаточны или небезопасны:
- IP-адреса можно подделать, не подходят для пользовательской аутентификации
- Статичные токены небезопасны, их сложно отзывать
- Указание HTTP-метода не обеспечивает безопасность, это часть спецификации REST
Вопрос 21

Как принцип HATEOAS помогает REST API быть более гибким и самодостаточным?

📌 Объяснение:
HATEOAS (Hypermedia As The Engine Of Application State) — принцип REST, при котором сервер включает в ответ ссылки на возможные действия:

Пример ответа с HATEOAS:
{
  "order": {
    "id": 123,
    "status": "pending",
    "_links": {
      "self": "/orders/123",
      "cancel": "/orders/123/cancel",
      "pay": "/orders/123/payment"
    }
  }
}
Вопрос 22

Клиент отправляет запрос на добавление товара в корзину. Какие статусные коды HTTP возвращаются в случае успеха?

📌 Объяснение:
Для операции "добавление товара в корзину" могут использоваться:

1. 200 OK — если корзина уже существует и товар добавлен в существующую корзину
2. 201 Created — если корзина создаётся впервые при добавлении первого товара

Нюансы:
- 201 Created обычно возвращается при создании нового ресурса с указанием его местоположения в заголовке Location
- 200 OK — для успешного обновления существующего ресурса
- На практике часто используют 200 OK для обеих ситуаций, но стандарт допускает оба варианта
Вопрос 23

Какой транспортный протокол обычно используется для отправки SOAP-сообщений?

📌 Объяснение:
- HTTP — наиболее распространённый транспортный протокол для SOAP-сообщений в веб-сервисах
- SOAP может работать поверх разных протоколов (HTTP, SMTP, TCP, JMS), но HTTP является стандартом де-факто для веб-интеграций
- HTTP обеспечивает широкую поддержку, безопасность (HTTPS), кэширование и совместимость с существующей инфраструктурой

Почему не другие:
- TCP — может использоваться, но менее распространён для веб-сервисов
- FTP — для передачи файлов, не для SOAP-сообщений
- SMTP — для email, используется в специфических интеграциях, но не "обычно"
Вопрос 24

Если ты создаёшь API для банка с жёсткими правилами взаимодействия, какое преимущество даст подход CODE-FIRST?

📌 Объяснение:
CODE-FIRST подход — сначала пишется код, затем автоматически генерируется документация (WSDL для SOAP, OpenAPI для REST).

Преимущества для банка с жёсткими правилами:
1. Гарантия соответствия — документация всегда актуальна, так как генерируется из кода
2. Экономия трудозатрат — не нужно вручную поддерживать документацию
3. Снижение ошибок — исключаются расхождения между кодом и документацией

Важно: Для банков критична точность документации, так как партнёры и регуляторы требуют строгого соответствия спецификациям.
Вопрос 25

После написания кода для веб-сервиса, какой документ полезен для других разработчиков?

📌 Объяснение:
Спецификация API (например, OpenAPI/Swagger для REST или WSDL для SOAP) — это документ, который описывает:

- Доступные endpoints (URL)
- Методы HTTP (GET, POST и т.д.)
- Форматы запросов и ответов
- Параметры, заголовки, коды ошибок

Почему именно она:
1. Практическая полезность — разработчики могут сразу интегрироваться с API
2. Автогенерация — часто генерируется автоматически из кода
3. Стандартизация — понятный формат для всех разработчиков

Техническая документация — более широкое понятие, может включать спецификацию API, но не является максимально конкретным и полезным для интеграции.
Вопрос 26

Если в процессе разработки API для онлайн-магазина постоянно меняются требования, какой подход обеспечит большую гибкость?

📌 Объяснение:
CODE-FIRST (сначала код, потом контракт) обеспечивает большую гибкость при часто меняющихся требованиях:

1. Быстрые итерации — можно менять код, а документация обновится автоматически
2. Меньше бюрократии — не нужно постоянно обновлять контракт вручную
3. Гибкость разработки — проще экспериментировать и вносить изменения

CONTRACT-FIRST (сначала контракт, потом код) более жёсткий:
- Требует согласования контракта до начала разработки
- Изменения контракта требуют пересогласования
- Лучше подходит для стабильных проектов с чёткими требованиями

Для онлайн-магазина с меняющимися требованиями CODE-FIRST предпочтительнее.
Вопрос 27

Почему REST API проектируется как stateless (без состояния)?

📌 Объяснение:
Stateless (без состояния) в REST означает, что каждый HTTP-запрос содержит всю необходимую информацию для его обработки. Сервер не хранит состояние клиента между запросами.

Преимущества stateless:
1. Масштабируемость — любой сервер может обработать любой запрос, нет привязки к конкретному серверу
2. Надёжность — нет риска потери состояния при падении сервера
3. Простота — не нужно синхронизировать состояния между серверами
4. Кэширование — запросы могут кэшироваться, так как они самодостаточны

Вариант с кэшированием частично верен, но не является основной причиной stateless архитектуры.
Вопрос 28

Какие форматы данных чаще всего используются при генерации кода и документации в контексте API?

📌 Объяснение:
В контексте API генерация кода и документации чаще всего использует:

1. JSON — для REST API (OpenAPI/Swagger спецификации в JSON/YAML)
2. XML — для SOAP API (WSDL документы в XML)
3. YAML — альтернатива JSON для OpenAPI спецификаций

Почему именно они:
- Машиночитаемость — могут обрабатываться инструментами генерации кода
- Стандартизация — форматы понятны и поддерживаются множеством фреймворков
- Интеграция — легко интегрируются в CI/CD процессы

HTML/CSS — для визуального представления документации, а не для генерации кода.
TXT/PDF — для человекочитаемой документации, но не для автоматической генерации кода.
Вопрос 29

Ты разрабатываешь новый интерфейс для веб-приложения. Какое преимущество даёт использование прототипов на разных этапах проектирования?

📌 Объяснение:

Вопрос 32

Ты моделируешь систему обработки заказов в интернет-магазине. Какой элемент DFD лучше всего подходит для обозначения заказа, поступившего от клиента?

📌 Объяснение:
В DFD (Data Flow Diagram — диаграмме потоков данных) элементы имеют разные назначения:

1. Поток данных (Data Flow) — "Заказ" — перемещение данных между процессами, хранилищами и внешними сущностями (клиент → система)
2. Хранилище данных (Data Store) — "Заказы" — место хранения данных (база данных)
3. Процесс (Process) — "Обработка заказа" — преобразование данных
4. Внешний агент (External Entity) — "Клиент" — источник или получатель данных

Заказ, поступивший от клиента — это данные в движении, следовательно, это поток данных, который идёт от внешнего агента "Клиент" к процессу "Обработка заказа".
Вопрос 33

Ты работаешь над проектом по разработке системы управления библиотекой. Какой элемент DFD ты будешь использовать, чтобы обозначить процесс выдачи книг?

📌 Объяснение:
В DFD (Data Flow Diagram) элементы имеют строгие назначения:

Процесс (Process) — преобразование или обработка данных:
- Пример: "Выдача книги", "Обработка заявки", "Формирование отчёта"
- Обозначается: прямоугольник с закруглёнными углами или круг

Поток данных (Data Flow) — движение данных между элементами:
- Пример: "Запрос на выдачу", "Информация о книге", "Данные читателя"
- Обозначается: стрелка

В контексте библиотеки:
- "Выдача книг" — это процесс, который преобразует данные (получает запрос → обновляет статус книги → записывает выдачу)
- "Запрос на выдачу" или "Информация о книге" — это потоки данных, которые входят в процесс или выходят из него
Вопрос 34

При интеграции двух систем учёта, каким образом CONTRACT-FIRST гарантирует правильное взаимодействие?

📌 Объяснение:
CONTRACT-FIRST подход в интеграции означает:

1. Сначала контракт — создаётся формальная спецификация (WSDL для SOAP, OpenAPI для REST)
2. Затем код — код клиента и сервера генерируется автоматически на основе контракта
3. Гарантия соответствия — обе системы следуют одному контракту, минимизируя риски несовместимости

Для интеграции двух систем учёта это особенно важно:
- Исключаются расхождения в форматах данных
- Снижаются ошибки ручной реализации
- Упрощается поддержка и изменение API

CODE-FIRST (разрабатывается код, а документация создаётся позже) не гарантирует правильность взаимодействия, так как возможны расхождения между реализациями.
Вопрос 35

Разрабатывая API для управления профилями пользователей, какие HTTP-методы ты бы использовал для создания, чтения, обновления и удаления данных?

📌 Объяснение:
Стандартные HTTP-методы для операций CRUD в REST API:

ОперацияHTTP-методПример использования
Create (Создание)POSTСоздание нового профиля пользователя
Read (Чтение)GETПолучение данных профиля по ID
Update (Обновление)PUT или PATCHПолное обновление профиля (PUT) или частичное (PATCH)
Delete (Удаление)DELETEУдаление профиля пользователя
Почему именно эта комбинация:
- GET, POST, PUT, DELETE — стандартный набор для RESTful API (CRUD операции)
- PATCH может дополнять PUT для частичного обновления
- OPTIONS, HEAD, CONNECT, TRACE — служебные методы, не для основных операций
- ALL — не является реальным HTTP-методом
Вопрос 36 (несколько вариантов)

Ты создаёшь API для приложения интернет-банкинга. Почему важно использовать аутентификацию, какие задачи она решает? Выбери все подходящие варианты.

📌 Объяснение:
Аутентификация в API интернет-банкинга решает критически важные задачи:

1. Безопасная передача данных — подтверждает личность клиента, предотвращает несанкционированный доступ
2. Контроль доступа (авторизация) — определяет, к каким ресурсам (счета, переводы, история) пользователь имеет право доступа

Неправильные варианты:
- Доступ без идентификации — противоречит самой сути аутентификации
- Упрощение разработки — аутентификация скорее усложняет разработку, но это необходимая мера безопасности

Для банкинга особенно важно:
- Соответствие требованиям регуляторов (ЦБ, PCI DSS)
- Защита финансовых данных и транзакций
- Предотвращение мошенничества
